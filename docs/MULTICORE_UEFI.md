# Forest OS – Multicore and UEFI Notes

This document consolidates the new multicore groundwork and the refreshed UEFI
boot path so that developers have a single reference for SMP, multikernel ideas,
and firmware expectations.

## 1. Multithreaded kernel background

A multithreaded kernel executes multiple kernel threads concurrently. When the
system also supports SMP, those threads run in parallel across CPU cores,
allowing process scheduling, memory management, and I/O paths to overlap. The
kernel must provide:

- **Scheduling primitives** – keeping runnable work balanced across BSP/APs.
- **Synchronization** – spinlocks, atomics, and wait queues to avoid races and
  deadlocks.
- **Per-CPU state** – separate stacks, TLS, and statistics per logical core.

Without real SMP hardware a kernel may still be “multithreaded” by time slicing,
but the gain is largely an illusion. True multicore hardware is what allows the
system to scale.

## 2. Forest OS SMP bring-up

The kernel now parses the ACPI MADT (“APIC”) table and records each LAPIC or
x2APIC entry that firmware exposes. The new `smp_init()` routine:

1. Locates the MADT via ACPI/uACPI.
2. Maps the LAPIC MMIO window to read the BSP APIC ID.
3. Registers every enabled processor entry into `smp_state_t`.
4. Reports the topology through `smp_get_state()` so schedulers and diagnostics
   can enumerate cores.

Today only the BSP is brought online, but per-core metadata, online counters,
and helpers such as `smp_mark_cpu_online()` are in place so the task scheduler
can wake APs in a future patch set. Until then, the infrastructure ensures we
properly name RTX/desktop CPUs and all major hypervisors’ virtual CPUs.

## 3. Multikernel model (design outlook)

Traditional SMP kernels share a single global memory space. A multikernel treats
each core (or core cluster) as a distributed node that communicates purely via
message passing. Benefits:

- Heterogeneous processors can run tailored kernels (e.g., mixing wide-vector
  X280 cores with lightweight P670 cores).
- Scalability improves because shared-memory contention is reduced.

Drawbacks include higher messaging overhead and the need for explicit resource
partitioning. Forest OS keeps the door open for experimentation: the ACPI/SMP
abstractions expose per-core IDs that a multikernel prototype could pin tasks
to, with shared memory reserved strictly for message buffers.

## 4. UEFI boot path

Modern PCs ship with UEFI firmware. Compared to legacy BIOS, UEFI:

- Provides a standard boot services API (system table, runtime protocols).
- Loads PE/COFF executables (`BOOTIA32.EFI`, `BOOTX64.EFI`) from a FAT ESP
  instead of executing an MBR stub.
- Offers Secure Boot (PK/KEK/db/dbx) and optional CSM for BIOS compatibility.

Forest OS now bundles GRUB stand-alone EFI binaries for both IA32 and x86_64.
`make iso` requires `grub-mkstandalone` and drops the resulting binaries inside
`ISO/EFI/BOOT/`. Testing tips:

- **VirtualBox** – enable “Enable EFI (special OSes only)” if you want firmware
  to use the EFI path instead of BIOS. The VBox-provided OVMF build includes the
  necessary GOP framebuffer.
- **QEMU + OVMF** – install the `ovmf` package on your distro and launch with
  `qemu-system-x86_64 -bios /usr/share/OVMF/OVMF.fd -cdrom forest.iso -m 1024`.
- **Secure Boot** – currently unsupported; disable it or enroll a devel key
  (Shim/MOK style) before booting unsigned kernels.

UEFI images remain FAT32/GPT formatted, so they work equally on class 2 (CSM
capable) and class 3 (pure UEFI) systems.

## 5. Quick reference

- `smp_get_cpu_count()` – returns how many logical processors firmware exposed.
- `smp_get_cpu(i)` – per-core metadata (ACPI UID, APIC ID, BSP flag).
- `smp_mark_cpu_online(apic)` – helper for future AP bring-up code.
- `EFI/BOOT/BOOTIA32.EFI` / `BOOTX64.EFI` – GRUB stand-alone binaries inside
  every ISO generated by `make iso`.

Use this page as the jumping-off point whenever you work on scheduler scaling,
message-passing experiments, or OVMF test automation.
